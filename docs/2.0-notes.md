# Norma 2.0 — deferred breaking changes

These behaviors are **intentional to keep in 1.9.x** so the modernization release stays non-breaking.
They are candidates for a **2.0** major where callers must opt in or migrate.

Source of truth for repros: `master` / 1.9.0 baseline (`Norma.normalize/2`, `Norma.Utils.form_url/1`).
All snippets below were run against that tree; expected strings are characterization of **today**, not the desired end state.

---

## 1. `form_query` drops duplicate keys and alphabetizes

**Where:** `Norma.Utils.form_query/1` in `lib/norma/utils.ex`

```elixir
defp form_query(query), do: "?" <> (query |> URI.decode_query() |> URI.encode_query())
```

**Mechanism**

| Step | Elixir stdlib | Effect |
|------|---------------|--------|
| `URI.decode_query/1` | builds a **map** | duplicate keys collapse; **last** value wins |
| `URI.encode_query/1` | emits keys in **sorted** order | query string is alphabetized |

So every normalize that rebuilds the URL through `form_url` rewrites the query, even when no query-related option is set.

### Repro — duplicate keys dropped

```elixir
iex> Norma.normalize("http://example.com?z=1&a=2&z=3&b=4")
"http://example.com?a=2&b=4&z=3"
# first z=1 is gone; z keeps last value "3"

iex> Norma.normalize("http://example.com?tag=a&tag=b&tag=c")
"http://example.com?tag=c"
```

### Repro — keys alphabetized (order not preserved)

```elixir
iex> Norma.normalize("http://example.com?m=1&c=2&a=3")
"http://example.com?a=3&c=2&m=1"

iex> Norma.normalize("http://example.com?a=3&c=2&m=1")
"http://example.com?a=3&c=2&m=1"
# both inputs collapse to the same ordered query
```

Covered today by tests under `"query params"` / `"sorts query params"` in `test/norma_test.exs`
(sort is asserted as correct product behavior).

### Why break it in 2.0

- **Duplicate keys are legal** in application/x-www-form-urlencoded (e.g. `?id=1&id=2`).
  Collapsing to a map is lossy for multi-value params and for “first wins” semantics.
- **Stable order** matters for cache keys, signatures, and golden string comparisons that expect
  input order (or server-defined order), not alphabetical rewrite.
- Alphabetizing is a side effect of the map round-trip, not a documented normalize option.

### 2.0 direction (sketch only)

- Prefer a list-preserving parse/encode path (e.g. keep pairs, or use a multi-value API).
- If sorting remains desirable, expose it as an **opt-in** (e.g. `%{sort_query: true}`), default off.
- If last-wins collapse remains desirable, same: opt-in, not silent.

## 2. `@masked_ports` ignores scheme

**Where:** `Norma.Utils.@masked_ports` + `form_port/1` in `lib/norma/utils.ex`

```elixir
@masked_ports ["443", "80", "8080", "21"]

defp form_port(port) when port in @masked_ports, do: ""
defp form_port(port), do: ":" <> port
```

`form_url/1` always does `form_port(port |> to_string)` and **never consults `scheme`**.

Any port in that set is stripped, including non-default ports for the active scheme
(e.g. HTTP on 443, HTTPS on 80, HTTP on 8080, HTTP on 21).

### Repro — scheme-agnostic strip (via `normalize/2`)

```elixir
iex> Norma.normalize("http://example.com:443")
"http://example.com"   # :443 removed even though default for http is 80

iex> Norma.normalize("https://example.com:80")
"https://example.com"  # :80 removed even though default for https is 443

iex> Norma.normalize("http://example.com:8080")
"http://example.com"   # 8080 is never a scheme default in URI, but still masked

iex> Norma.normalize("https://example.com:443")
"https://example.com"  # correct for https (default port)

iex> Norma.normalize("http://example.com:80")
"http://example.com"   # correct for http (default port)
```

### Repro — same rule on raw `form_url/1` (including short hosts)

`normalize/2` rejects hosts without a `.` (`is_url?/1`), so short hosts only show the bug through `form_url/1`:

```elixir
iex> Norma.Utils.form_url(URI.parse("http://h:443"))
"http://h"             # task-stated case: http://h:443 -> http://h

iex> Norma.Utils.form_url(URI.parse("https://h:80"))
"https://h"
```

### Interaction with scheme inference

When the input has no scheme, port still drives scheme via `port_handler/1`, then the port is masked:

```elixir
iex> Norma.normalize("//example.com:443")
"https://example.com"

iex> Norma.normalize("//example.com:8080")
"http://example.com"
```

That pairing (infer scheme from port, then drop the port) is coherent for default ports, but still wrong for **explicit** `http://…:443` / `https://…:80` where the port carries meaning.

### Why break it in 2.0

- RFC 3986 default-port omission is **scheme-relative**. Omitting `:443` on `http:` changes authority semantics for clients that treat non-default ports as significant.
- Masking `8080` and `21` always is especially aggressive: those are not universal defaults for `http`/`https`.
- A future collapse of `form_url` onto `URI.to_string/1` (1.9 exploration) would still need an explicit policy for this list.

### 2.0 direction (sketch only)

- Mask only the **default port for the current scheme** (e.g. 80 for `http`, 443 for `https`, 21 for `ftp`).
- Drop or rethink hard-coded `8080` unless product intent is “always hide common alt HTTP”.
- Keep inference from port when scheme is missing as a separate step; do not strip non-default ports after an explicit scheme is present.

## 3. `add_trailing_slash` extension heuristic breaks versioned paths

**Where:** `Norma.Normalizer.add_trailing_slash/1` in `lib/norma/normalizer.ex`

```elixir
defp add_trailing_slash(url = %URI{path: path}) do
  if path && (String.contains?(path, ".") || String.ends_with?(path, "/")) do
    url
  else
    url |> Map.put(:path, "#{path}/")
  end
end
```

**Heuristic:** any path that **contains a `.` anywhere** is treated as a “file” and skips the trailing slash.
That false-positives on version segments (`v1.2`), dotted API prefixes (`api.v2`), and any intermediate dotted directory.

### Repro — versioned directory does not get `/`

```elixir
iex> Norma.normalize("http://example.com/v1.2/docs", %{add_trailing_slash: true})
"http://example.com/v1.2/docs"
# expected directory-style: .../docs/  — not applied because of the '.' in "v1.2"
```

### Repro — contrast with undotted path and real files

```elixir
iex> Norma.normalize("http://example.com/docs", %{add_trailing_slash: true})
"http://example.com/docs/"
# works when no '.' appears in the path

iex> Norma.normalize("http://example.com/sitemap.xml", %{add_trailing_slash: true})
"http://example.com/sitemap.xml"
# intended: leaf file-like path keeps no slash

iex> Norma.normalize("http://example.com/api.v2/users", %{add_trailing_slash: true})
"http://example.com/api.v2/users"
# dotted segment in the middle also blocks the slash
```

### Why break it in 2.0

- `String.contains?(path, ".")` is not an extension check; it is a global path scan.
- Versioned REST trees (`/v1.2/...`, `/releases/1.2/...`) are common and are directories, not files.
- True extension detection should look at the **final segment** only (and still be imperfect for extensionless files).

### 2.0 direction (sketch only)

- Prefer “final segment contains `.`” (or a small allowlist of extensions) instead of “`.` anywhere”.
- Or always add `/` when `add_trailing_slash: true` except when the path already ends with `/`
  (and document that file-like paths need an explicit opt-out).
- Keep the existing “do not double `/`” behavior.

## Out of scope for 1.9.0

| Topic | 1.9.0 | 2.0 |
|-------|-------|-----|
| Query map round-trip (drop dups + sort) | keep | redesign |
| Scheme-blind `@masked_ports` | keep | scheme-aware defaults |
| Dotted-path trailing-slash skip | keep | segment/extension-aware |
| Code changes in this document | none | — |

1.9.0 only modernizes non-behavioral surface (structs/specs, package metadata, golden characterization of **current** strings including these bugs). See the golden suite lane for lock-in tests.

## Checklist for a future 2.0 PR

1. Flip or replace each behavior behind explicit options or new defaults; bump major version.
2. Update golden suite expectations in the same PR (do not “fix” goldens silently on 1.x).
3. Document migration: before/after strings for the three families above.
4. Call out any collapse of `form_url` onto `URI.to_string/1` and how it interacts with port masking and query encoding.
